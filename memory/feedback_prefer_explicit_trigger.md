ユーザー可視な値を出す機能は、**明示的な操作で 1 回計算し、結果を `Scene.silicone_molding` に保存して、`Panel.draw` は保存された値を読んで整形するだけ** にする。`draw()` の中で depsgraph 評価やジオメトリ走査を行う「常時ライブ更新」型の設計は選ばない。

**Why:** 2026-08-14 の体積計測機能で、最初は「キャッシュを持たず `draw()` のたびに再計算」で仕様を固めた（ユーザーの当初の合意事項でもあった）。その後ユーザーから「ボタンを押して体積計算を行います。表示された結果をクリックでコピーです」と設計変更が入り、オペレータ起動 + `Scene` への結果保存に切り替えた。得られたものが大きい:

- リドローが計測コストを払わなくなり、`DEFAULT_CLOSED` にするか・キャッシュを入れるかという性能の議論そのものが消えた
- エラー伝達が `Panel.draw` の行（`self.report` が使えない）から `self.report({"ERROR"}, ...)` + `{"CANCELLED"}` に移り、Blender 標準の作法に乗った
- **テスト可能性が跳ね上がった。** 「`draw()` の中にしかない値」は tier 1・tier 2 のどちらからも到達できず、受け入れ基準の多くを「レビューでの目視」に落とすしかなかった。結果が `Scene` プロパティに載ると、オペレータを呼んで値を読むだけで自動検証できる。tier 2 も extension モジュールを import せず `bpy.ops` と RNA だけで完結する

代償はスナップショットが古くなること（自動無効化しない）。ハンドラ購読は投機的複雑性として入れない、という判断でこれを受け入れた。

**How to apply:**

- 新機能の仕様で「パネルに数値を出す」要求が来たら、まずボタン起動 + 結果保存で設計する。ライブ更新を選ぶのは、ユーザーが明示的にそれを求めた場合だけ
- 結果は「値の `FloatProperty` 等」と「`<名前>_measured` の `BoolProperty`」の対で持つ。整形済み文字列を `Scene` に置かない（データは数値、整形は UI 層）
- 値は表示単位で保存する（例: cm³）。内部単位で保存すると、後から `scale_length` が変わったときにスナップショットが崩れる
- 結果を書き換えるオペレータは `bl_options` に `UNDO` を含める。クリップボードコピーのような読み取り専用オペレータには含めない
- 失敗時は前回の結果を残さず「未計測」に戻す。古い数値が見えていると、それが今の対象の値だと誤読される
- ハンドラ (`depsgraph_update_post`)、タイマー、キャッシュは足さない。鮮度はユーザーが押し直すことで担保する
